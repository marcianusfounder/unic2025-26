2. Projeto

O projeto é uma fase intensiva na qual se busca dar

resposta à pergunta: “qual é a solução?”.

A documentação engloba:

• Estrutura de dados.

• Arquitetura do software.

## Página 19

DIMENSÃO DO DESENVOLVIMENTO

2. Projeto

A tarefa de projeção também incorpora: • A projeção de dados, que transforma o modelo de domínio da informação criada durante a análise nas estruturas de dados a serem necessárias à implementação do software.

• O projeto arquitetônico, que define a relação entre os principais elementos estruturais do software; os padrões de projeção, que possam ser utilizados visando satisfazer os requisitos já definidos para o sistema, e; as restrições, que afetam a maneira com que se possam aplicar os padrões arquitetônicos do projeto.

• O projeto da interface, que descreve a maneira como o software se comunica consigo mesmo, com os sistemas que nele interoperam e com as pessoas que o utilizam.

• O projeto em termos de componentes, que transforma os elementos estruturais da arquitetura do software numa descrição procedimental dos componentes do software.

## Página 20

DIMENSÃO DO DESENVOLVIMENTO

3. Implementação

Nessa fase, deseja-se responder à pergunta: “como se  constrói a solução?”

Para isso, utilizando-se linguagens de programação que geram o código- fonte, sendo necessário inspecionar o código, verifica-se:

• Uniformidade na escritura.

• Ausência de ambiguidades.

• Pureza sintática.

• Semântica do problema e não da tecnologia.

• Compactação do código em unidades lógicas distinguíveis (bibliotecas,

rotinas, procedimentos).

• Localização precisa do código que satisfaz uma exigência.

• Linearidade ou acompanhamento de um fluxo lógico e coerente.

## Página 21

DIMENSÃO DO DESENVOLVIMENTO

4. Teste A fase de teste pretende responder à pergunta: “o problema

foi resolvido?”.

Os princípios de um teste: • A todos os testes se deve dar um acompanhamento até cobrir as exigências do cliente. • Os testes devem ser planejados bem antes de serem efetuados. • Os testes devem ser iniciados primeiro ‘pelo menor’, progredindo-se para “o maior”. • Os testes devem ser conduzidos por uma equipe independente.

## Página 22

DIMENSÃO DO DESENVOLVIMENTO

4. Teste

TIPOS DE TESTE

Teste de caixa branca. É um método de concepção de casos de teste que utiliza a estrutura de controle do projeto procedimental para a obtenção dos casos de teste. O engenheiro do software pode obter casos de teste que:

✓Garantam sejam exercitados, pelo menos uma vez. ✓Exercite todas as decisões lógicas em suas vertentes

verdadeira e falsa. ✓Execute todos os laços em seus limites e com seus limites

operacionais. ✓Se baseie no minucioso exame dos detalhes dos procedimentos.

## Página 23

DIMENSÃO DO DESENVOLVIMENTO

4. Teste

TIPOS DE TESTE

Teste de caixa preta. O teste de caixa preta centra-se nos requisitos funcionais do software. Permite ao engenheiro do software obter conjuntos de condições de entrada que exercitem completamente todos os requisitos funcionais de um programa. O teste de caixa preta não é uma alternativa para as técnicas de teste de caixa branca. Trata-se de um enfoque complementar que tenta descobrir diferentes tipos de erros não procurados com os métodos de caixa branca.

Tenta encontrar erros das seguintes categorias: ✓Funções incorretas ou ausentes. ✓Erros de interface. ✓Erros nas estruturas de dados ou em acessos às bases de

dados externas. ✓Erros de rendimento. ✓Erros de inicialização e encerramento.

## Página 24

DIMENSÃO DO DESENVOLVIMENTO

TIPOS DE TESTE 4. Teste Teste de unidade. Centra o processo de verificação na menor unidade do projeto do software: o módulo. É orientado à caixa branca e esse passo pode ser efetuado paralelamente para vários módulos. Testes que se dão como partes do teste de unidade:

Teste da interface do módulo, visando garantir flua a informação adequadamente para e a partir da unidade de programa que está sendo testada. Teste das estruturas de dados locais, visando garantir a manutenção temporária dos dados, conservando-se sua integridade durante todos os passos de execução do algoritmo. Testes das condições de limite, visando garantir o funcionamento correto do módulo nos limites estabelecidos como restrições de processamento; são testados os caminhos independentes da estrutura de controle no intuito de se garantir que todas as sentenças do módulo se executam pelo menos uma vez. Teste de todos os caminhos de manejo de erros.

## Página 25

DIMENSÃO DO DESENVOLVIMENTO

TIPOS DE TESTE 4. Teste

Teste de validação. A validação é alcançada quando o software funciona de acordo com as expectativas razoáveis do cliente. Efetuam-se dois testes:

✓O teste Alfa, que se realiza no local de desenvolvimento, mas por

um cliente, sendo usado o software tendo-se o desenvolvedor como observador do usuário, registrando-se erros e problemas de uso.

✓O teste Beta, efetuado pelos usuários finais do software em seus

respectivos locais de trabalho; como o desenvolvedor normalmente não está presente, o teste beta é uma aplicação ao vivo do software num ambiente que não pode ser controlado por ele; é o cliente quem registra os problemas, informando-os ao desenvolvedor.

## Página 26

DIMENSÃO DO DESENVOLVIMENTO

TIPOS DE TESTE 4. Teste

Teste do sistema. O propósito primordial de sua realização é testar profundamente o sistema, verificando-se a adequada integração de todos os elementos do sistema e a realização das  pertinentes funções.

## Página 27

DIMENSÃO DO DESENVOLVIMENTO

5. Entrega e manutenção

Enquanto a entrega pretende que o cliente possa utilizar a solução e contar com a garantia de mostrar-se operacional, a fase de manutenção busca responder a pergunta: “são necessários aperfeiçoamentos/alterações”?

• Corretivos, para reparação de erros. • Adaptativos, para modificação do software, adaptando-o às mudanças do ambiente de trabalho. • Perfectivos, para inserir novas funcionalidades em virtude de novas exigências. • Preventivos, para melhorar a manutenção do sistema e antecipar erros.

## Página 28

DIMENSÃO DO DESENVOLVIMENTO

5. Entrega e manutenção

Há os seguintes tipos de manutenção:

• Manutenção corretiva: diagnostica e corrige erros; implica altos custos.

• Manutenção adaptativa: apresenta-se quando se fazendo necessária uma mudança de ambiente ou mudança na plataforma de trabalho.

• Manutenção perfectiva: faz-se quando da necessidade de aperfeiçoamentos e adição de novas capacidades.

• Manutenção preventiva: para o aperfeiçoamento da futura manutenção.

## Página 31

DIMENSÃO ORGANIZACIONAL

EQUIPE DE TRABALHO

• ISOMÓRFICA

A equipe isomórfica organiza-se de acordo com a estrutura dos principais módulos de software. Cada membro da equipe está ligado a um módulo de software específico, do início ao fim.

AS VANTAGENS DESSA ESTRUTURA:

• É organizacionalmente simples.

• Muitas tarefas são desenvolvidas paralelamente.

• As tarefas podem ser claramente definidas e compreendidas.

## Página 32

• As equipes isomórficas se adéquam a projetos nos quais os módulos de software são relativamente independentes dos outros. • A maior desvantagem desse tipo de equipe está em poder conduzir a dificuldades na integração dos módulos, por problemas de comunicação entre os desenvolvedores.

## Página 33

DIMENSÃO ORGANIZACIONAL

EQUIPE DE TRABALHO

• ESPECIALISTA

Nesse tipo de estrutura, cada membro da equipe se dedica à resolução de tarefas e temas relacionados a sua área de conhecimento ou de especialidade ao longo de todos os módulos ou tarefas a cumprir em um projeto

A vantagem desse tipo de projeto está em permitir o máximo aproveitamento potencial e a eficiência de cada especialista. A desvantagem relaciona-se a dificuldades de integração, à carência de unidade no módulo (cada especialista desenvolve o seu) e a problemas de monitoramento e acompanhamento com relação à contribuição de cada especialista.

## Página 34

DIMENSÃO ORGANIZACIONAL

EQUIPE DE TRABALHO

• DEMOCRÁTICA

Esse tipo de estrutura de equipe, chamado em certas ocasiões de autogerenciada, tem uma estrutura relativamente informal

• A tomada de decisões é compartilhada pelos membros. • A estrutura promove e fortalece a comunicação e a interação entre os membros.

A vantagem desse tipo de equipe está no fato de operar bem em projetos de desenvolvimento essencialmente pequenos, nos quais a inovação e a criatividade são fatores mais importantes do que o cumprimento de prazos estritos. A desvantagem está no fato de não serem efetivas. Suas falhas decorrem da circunstância de seus membros, particularmente pessoas de grande talento, terem um forte ego, ocorrendo conflitos de cunho interpessoal. Outro problema ligado a essas equipes é a tendência a evoluírem sem liderança em razão de sua ausência.
